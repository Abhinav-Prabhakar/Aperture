Append-only. The component renders entries; it never rewrites them.

export: CSV · JSON · reconciled

Forty-eight raw records become forty included. Two duplicates and two haemolysed samples leave first, then two withdrawn consents, one outlier, and one exhausted aliquot. The imputation and the unit conversion change values without changing the row count. Filter by kind and note that the export stays chronological.

What it checks

  • The chain is continuous. Each entry must start where the previous one ended. A gap is a missing step, and the header says so instead of quietly reporting the last count.
  • The arithmetic is shown. raw − removed + added = included is printed with the actual numbers. A reader can check it without trusting the component.
  • Exclusions are counted by reason. The "why rows left" panel groups removals by reason code, so the methods paragraph writes itself: four haemolysed, two withdrawn consents, one outlier.
  • Transformations are distinct from exclusions. A log transform, an imputation, and a unit conversion appear as their own kinds. They matter even when the row count does not move.
  • Reversibility is explicit. "Yes" means the step can be undone from the recorded inputs; "No" means the sample or the consent is gone. Reviewers ask this.
  • The export is the record. CSV for a supplement, JSON for the archive. Both carry every entry, not the filtered view.

How reconciliation works

Entries are sorted by at and read as a sequence. The first rowsBefore is the raw count; the last rowsAfter is the included count. Every negative delta is a removal and every positive delta an addition. If two adjacent entries disagree, the component reports the first disagreement by index, expected count, and found count.

  • This is a review aid, not a database constraint. The component cannot stop a team from editing its own source data. It can make an inconsistent ledger impossible to miss.
  • One target per ledger. Counts only reconcile when every entry applies to the same record set. Use a separate ledger for a separate table.
  • Reason codes are yours. HEM, CONSENT, and OUTLIER_4SD are strings; Aperture does not impose a taxonomy.

Data contract

  1. Entry. id, kind (exclusion, transformation, imputation, conversion), action, target, reason, reasonCode, actor, at, rowsBefore, rowsAfter, reversible, optional linkedRun and note.
  2. Timestamps. ISO 8601 strings. They are displayed as day, month, and time, and sorted lexically, which is correct for ISO.
  3. Counts. Non-negative integers. Values are clamped for the summary, but the table shows what was recorded.
  4. Export. onExport receives { csv, json }. ledgerCsv, ledgerJson, and summarizeLedger are exported as pure helpers.
  5. Display order. Newest first on screen; chronological in every export. The footer says so.

Accessibility

  • The ledger is a table with a caption and a row header per entry; the step, reason, code, and actor are all text.
  • Reconciliation state is announced as text, not only as a tint. The warning icon has an accessible label through the sentence beside it.
  • Kind filters are buttons with aria-pressed, and the current filter is visible.
  • The horizontal layout collapses at 640 px; actor and kind move into the step cell rather than forcing a sideways scroll.
  • No motion beyond a hover tint. The ledger is a record, not a feed.

Status

Ready. It is the smallest instrument in the pack and the one that most often changes a conversation: the first time a team sees n = 40 next to the eight records that left, the methods paragraph gets written from the ledger instead of from memory.
